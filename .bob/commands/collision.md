---
description: Analyze two Git branches and verify a behavioral collision with fresh evidence
argument-hint: <branchA> <branchB> [requirements-ref:path]
---
Analyze branches $1 and $2. Optional requirements source: $3. Use the arguments supplied after /collision; ask only for missing branch names. Work in Agent mode with terminal access. Read docs/collision-workflow.md first.

1. Run `git status --short --branch`. Preserve current changes, branch tips, and the existing demo runner. Never reset, force-push, switch the user's branch, or edit production code to manufacture a failure.
2. Run `node scripts/collision-workflow.mjs prepare <branchA> <branchB> [requirements-ref:path]`, passing the actual values as quoted arguments. Record the printed directory. This pins refs, finds their merge-base, and saves diffs and the requirements if supplied. If refs are absent or unrelated, report the blocker; never auto-resolve it.
3. Read both diffs, then inspect dependencies and tests using `git show <pinned-sha>:<path>`. Read the actual requirements file. Missing requirements mean analysis proceeds without requirements claims, not that requirements may be inferred. Do not use demo explanations, hardcoded runner tests, existing fixes, or known scenario labels as evidence of fresh discovery. Existing comments that reveal a collision are evidence of a prepared fixture; disclose them.
4. Independently analyze each branch's changed inputs, outputs, invariants and consumers. If subagents are available, delegate one read-only branch analysis to each and one requirements analysis, in parallel. Otherwise perform these analyses sequentially and disclose that no subagents ran. Each returns pinned file/function citations and uncertainty. Compare the results for a changed invariant used by the other branch.
5. Save a pre-execution `hypothesis.md` in the analysis directory: behavior on A and B, expected combined behavior, specific incompatible assumption, source citations, requirement citations, and an observable assertion that could disprove the hypothesis. Distinguish an incompatibility hypothesis from a requirement violation already present on a branch.
6. Write a NEW `generated.test.mjs` beside the hypothesis. It will run at tests/collisionlab-generated.test.mjs in all three worktrees; import source via ../src/. Test externally observable behavior derived from contracts; never assert that the defect should occur, hardcode a branch name to force failure, modify production code, or copy the prebuilt collision test. Use the same test bytes across controls and combined code. Where a feature is absent on a control branch, explain applicability; missing imports are NOT successful controls. Prefer separate meaningful behavioral controls if the same test cannot apply, run them in additional detached worktrees, preserve logs and clean up only worktrees you created.
7. Run `node scripts/collision-workflow.mjs verify <analysis-directory>`. Read execution.json including full stdout/stderr for all runs. This command executes trusted local project/test code; worktrees isolate Git changes, not process or network access. Do not use it on unknown third-party code.
8. Produce `analysis.json` and `analysis.md` in the directory. Include branch SHAs, requirements provenance, hypothesis, source citations, generated test path/hash, actual assertion/expected/actual, control applicability, observed suite results, merge result, cleanup and measured execution durations. Set verdict to CONFIRMED, NOT_REPRODUCED, INCONCLUSIVE, TEXTUAL_CONFLICT, or ERROR. CONFIRMED requires both original branch suites pass, a genuinely clean merge, the intended behavioral assertion failing (not setup/import/syntax failure), and meaningful control evidence tying it to composition. Any unaccounted failure makes the conclusion INCONCLUSIVE. Mark regressions already detected by existing merged tests explicitly. If the test passes, say NOT_REPRODUCED; never claim the entire repository is conflict-free.
9. Suggest a minimal fix grounded in requirements, but do not apply it in this command. Report the analysis directory and limitations. The helper's FAILURE_REQUIRES_REVIEW is not CONFIRMED, and exit 0 means evidence collection completed, not that a collision exists. These reports are separate from the legacy dashboard schema; do not claim they appear there automatically.
